# DECISIONS — 판단 기록

> 만들면서 내린 중요한 결정과 그 이유. 형식: 결정 / 왜 / 틀린 것·고친 것.
> 실제 조직 정보는 쓰지 않는다. 예시는 가짜 회사 "한빛테크"뿐이다.

## 데이터와 보안
- 결정: **엔진(코드)과 데이터를 완전히 나눈다.** 저장소에는 가짜 회사 "한빛테크"와 `HB-` 가짜 ID만 두고, 실제 값은 실행 PC의 `data/`·`config.py`·`.env`에만 둔다(`.gitignore`)
  - 왜: 코드는 밖에 남겨도 되는 자산이고, 데이터는 조직 밖으로 나가면 안 되는 자산이다. 망이 분리된 환경에서도 코드는 한 방향(저장소 → 실행 PC)으로만 흐르게 한다
- 결정: **실제 메뉴 지도는 실행 PC 안에서 사내 AI와 엑셀로 만든다**(`docs/MAP_PROMPT.md`, 원칙 12가지). 외부 AI는 설계·코딩 코치 역할만 하고 실제 값을 받지 않는다
  - 왜: 조직 데이터를 외부로 보내지 않으면서도 데이터 정리에 AI의 도움을 받을 수 있다. 메뉴 ID는 사람이 직접 확인한다
- 결정: **읽기 전용 제품.** 시스템 로그인·자동 신청을 하지 않고, 링크를 보여 줄 뿐 누르는 것은 사람이다
  - 왜: 권한·승인 문제가 생기는 "실행형 에이전트"를 피하고, 사고 범위를 링크 안내로 묶는다

## 구조
- 결정: 메뉴 검색(1층)과 상황 체크리스트(2층)는 **LLM 없이** 키워드·동의어로 한다
  - 왜: GPU 없는 PC에서 LLM은 느리다. 찾는 게 분명한 질문은 규칙이 더 빠르고(1ms 안쪽) 매번 같은 답을 준다
- 결정: **AI(3층)는 규칙이 못 찾았을 때만, 챗봇 창에서만, 메뉴 지도 안의 ID만 고르게 한다.** AI가 확실하다(`sure=true`)고 할 때만 쓰고, 받은 ID는 지도에서 다시 확인해 없는 ID는 버린다. 애매하거나 메뉴와 상관없으면 거절한다
  - 왜: 없는 메뉴를 지어내지 못하게 막는다. 틀린 답보다 거절이 낫다. AI가 꺼지거나 연결이 끊겨도 1·2층은 그대로 돈다
- 결정: **메인 검색창은 규칙만** 쓰고, 못 찾으면 챗봇 창을 열어 같은 질문을 넘긴다. AI가 고른 답에는 "AI 추천" 표시를 붙인다
  - 왜: 메인은 늘 빠르고 같은 답이어야 믿을 수 있다. AI 답은 눈에 보이게 구분한다
- 결정: 설치 패키지 없이 **파이썬 표준 라이브러리 + HTML 파일 하나**(LLM 호출도 `urllib`, 외부 CDN·글꼴 없음)
  - 왜: 설치가 어렵거나 인터넷이 없는 PC에서도 파일만 옮기면 돌아간다
- 결정: 사내 AI는 **OpenAI 호환 API**로 부른다. 벡터 DB·임베딩 없이 작은 메뉴 지도를 목록 그대로 준다
  - 왜: 지도가 수백 줄 수준이라 RAG 인프라가 필요 없다. 부품이 적을수록 고장도 적다
- 결정: 데이터 원본은 **CSV**, 여러 값은 `|`로 나눈다. 데이터 검사기(`check_data.py`)를 둔다
  - 왜: 현업 담당자가 엑셀로 바로 고칠 수 있다. 검사기가 엑셀이 바꾼 숫자 ID·날짜 모양, 한 글자 키워드를 잡아낸다
- 결정: 회사마다 바뀌는 값(주소 틀, 화면 문구, 모델 주소, 키워드)은 **설정 파일에서만** 읽는다
  - 왜: 실행 PC에서는 `config.py` 하나만 고치면 된다

## 사용자 경험
- 결정: **모를 때는 연락처 대신 "부서 선배님께 편하게 여쭤보는 건 어떨까요?"처럼 대면 소통을 권한다**
  - 왜: 모르는 것을 지어내지 않고, 신입이 사람에게 묻기를 꺼리는 문제를 오히려 대화로 이어 준다. 길잡이는 사람 사이 대화를 대신하지 않고 이어 준다
- 결정: **입사 전 안내는 범위에서 뺀다.** 길잡이는 사내 PC를 받은 뒤부터만 맡는다
  - 틀린 것 / 고친 것: 처음에는 입사 30일 전부터 안내하려 했지만, 입사 전 신입은 사내 PC도 사내 포털 링크도 쓸 수 없다. 입사 전 안내는 채용 담당이 보내는 메일·문자 양식이 맡는 것으로 나눴다
- 결정: 일부 사용자만 열 수 있는 메뉴, 관리자용 할 일, 날짜별 타임라인은 화면에서 뺀다
  - 왜: 이 화면을 보는 사람은 신입·인턴이다. 열 수 없는 링크나 관리자 할 일은 혼란만 준다. 날짜보다 상황(손님 방문, 출장 …)으로 찾는 편이 단순하다

## 기록과 측정
- 결정: **익명 질의응답 기록을 제품의 목적으로 삼는다**(`LOG_ENABLED` 기본 True)
  - 왜: 신입·인턴이 무엇을 가장 궁금해하는지 데이터로 알고, 못 찾은 질문·틀린 답을 찾아 지도를 고치기 위해서다
  - 지키는 선: 사번·이름·IP·컴퓨터 이름·세션을 남기지 않고, 질문과 클릭을 잇지 않는다. 질문 속 긴 숫자·전화·메일은 저장 전에 가린다. 화면에 수집 안내(익명, 개선·통계에만, 평가 미반영)를 숨기지 않고 보인다. 통계는 5번 이상 묶음만, 90일 뒤 삭제. 도입할 때는 안내 문구와 보관 기간을 조직의 정책에 맞추고, 검토가 길어지면 설정 한 줄로 기록을 끈 채 먼저 연다
- 결정: 정답셋을 **"일상어"와 "메뉴 이름" 두 종류로 나눠** 채점하고, 기존 검색(흉내)과 비교한다
  - 왜: 메뉴 이름을 아는 사람에게는 기존 검색으로 충분하다. 이기는 곳과 비기는 곳을 정직하게 보여 준다
  - 주의: 가짜 데이터는 정답에 맞춰 만들었으므로 점수가 높게 나온다. 실제 성능은 실제 질문·실제 데이터로 다시 잰다
- 틀린 것 / 고친 것: 샘플 식사 상황의 키워드 "밥"이 한 글자라 검색에 안 걸렸다. 데이터 검사기가 잡아내 "밥 먹|밥 몇"으로 고쳤다
- 틀린 것 / 고친 것: 실제 환경의 AI가 생각 과정·코드 블록·설명 글이 섞인 답을 주어 JSON을 읽지 못했다. 답에서 JSON을 꺼내는 부분을 튼튼하게 고치고, 잘린 답은 따로 알리게 했다(`LLM_MAX_TOKENS`, `LLM_JSON_MODE` 설정 추가)
